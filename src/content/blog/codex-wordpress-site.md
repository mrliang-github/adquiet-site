我这次做独立站，没有直接用自己熟悉的 Next.js。

原因很简单：这次要做的不是一个只负责展示的页面。

它更像一个后面要持续运营的外贸独立站。

外贸独立站要管的东西，比几个页面多得多。

你后面会想加产品分类、产品详情、询盘表单、SEO 标题、博客内容、图片管理、支付、多语言、后台编辑。很多东西都不是一次做完就结束。

如果每一块都用 Next.js 自己写，当然可以。

问题是，它会慢慢变成另一个开发项目。

我这次不想这样。

我想先把一个能运营、能改内容、能上产品的站跑起来。

所以最后，我让 Codex 连接 VPS，帮我把 WordPress 先搭起来。

## 为什么这次没用我熟悉的 Next.js

如果只是做一个展示页，Next.js 很舒服。

页面怎么写，组件怎么拆，怎么部署，我都熟。

但独立站后面要处理的事更多。

比如产品页。

外贸老板不可能只放一个首页。后面肯定要有产品分类、详情页、参数、图片、询盘按钮。

再比如内容。

你要写博客、做 SEO 页面、改标题描述、加公司介绍、改图片。很多内容都需要后面反复调。

还有插件。

WordPress 里很多东西有现成插件：表单、SEO、缓存、多语言、图片压缩、备份、支付。虽然插件不能乱装，但至少不用每个功能都从头写。

如果我用 Next.js 做，这些也能做。

但我就要自己接后台、接表单、接内容管理、接图片、接 SEO 配置。

一开始看起来很自由。

做着做着，就会越来越重。

所以这次我没有用自己熟悉的方案硬做。

不是 Next.js 不好。

只是独立站这个场景，WordPress 更省事。

## Shopify 也不是我这次想要的

做独立站，很多人会先想到 Shopify。

这个选择没问题。

Shopify 后台成熟，商品、主题、支付、应用市场都比较完整。很多外贸团队用它，也很正常。

但我这次没有选 Shopify。

一个原因是类目和平台规则。

不同产品、不同业务形态，在 Shopify 这类平台上会有一些限制。你要测试一些方向时，心里会有顾虑。

另一个原因是自由度。

我这次想要一个更能自己控制的站。

服务器在自己这边。  
文件和数据库在自己这边。  
插件怎么装，页面怎么改，后面怎么接自动化，我可以慢慢试。

Shopify 更省心。

WordPress 更自由。

我这次需要的是后者。

## 真正卡我的，是 WordPress 这段

WordPress 适合这件事。

但我不熟。

这才是问题。

真正卡住我的，是 WordPress 的搭建流程。

VPS 环境怎么配。  
WordPress 怎么装。  
域名怎么指过去。  
HTTPS 怎么弄。  
后台哪些插件先装。  
页面打不开该查哪里。  
权限和备份要注意什么。

这些对专门做 WordPress 的人来说很基础。

但它们不是我的日常工作。

我当然可以自己搜教程。

但搜教程有个问题：很碎。

一个问题搜一篇文章，一个配置看一个视频。看完还要判断：这个教程适不适合我的服务器？适不适合现在这个版本？会不会把环境搞乱？

这次 Codex 帮到我的地方就在这里。

它只是帮我把不熟的 WordPress 搭建流程先跑通。

## Codex 具体帮我做了什么

我这次让 Codex 做的事，其实都很具体。

先看服务器能不能连。  
再看网站服务有没有跑起来。  
再看域名有没有指到这台服务器。  
再看浏览器会不会提示不安全。  
再看 WordPress 后台能不能进。

这些话换成技术词，就是 VPS、服务、端口、域名、证书、WordPress 配置。

但对普通外贸老板来说，不用先记这些词。

你只要知道一件事：

网站打不开时，不要一上来乱改。

先看是哪一层出问题。

以前我遇到这种问题，也会忍不住猜。

是不是 WordPress 装坏了？  
是不是服务器挂了？  
是不是域名还没生效？  
是不是 HTTPS 没弄好？

现在我可以直接把状态告诉 Codex，让它带着我一项项看。

它会提醒我先别乱动配置。

先确认服务器能不能连。  
再确认服务有没有启动。  
再确认域名有没有指过来。  
再确认后台能不能打开。

这个过程不神奇。

但很有用。

因为我不用每次都从零开始查教程。

## 我想解决的是后面持续修改

独立站真正麻烦的地方，常常在上线后。

你今天想改产品页。  
明天想加一个产品分类。  
后天想写一篇 SEO 文章。  
过几天又想换一批产品图。  
表单收不到邮件，还要查原因。

这些事情都不大。

但如果每次都要自己手动进后台、找位置、改内容、检查有没有改坏，就会很烦。

更麻烦的是页面风格。

如果要改整体视觉、产品页布局、按钮样式，很多时候还是得找设计或前端一起看。

这也是我为什么想用 Codex 做这件事。

我不是想证明 AI 可以一键建站。

我更想看的是：它能不能把这些反复手动处理的小事，先帮我拆开一点。

比如我想改页面结构，可以让它先给我方案。  
我想整理产品内容，可以让它先看表格。  
我想改 SEO 标题，可以让它先看页面和关键词。  
我想把 Google Drive 里的图片整理出来，也可以让它帮我拆步骤。

这些现在还没有全部跑得很顺。

但方向是对的。

以前我可能会因为不熟 WordPress，就继续用熟悉的 Next.js 硬做。

现在我可以选一个更适合独立站的方案，再让 Codex 帮我跨过前面那段不熟的配置。

这个变化不大。

但很实在。

## 我不会把网站全交给 AI

这部分要说清楚。

我不会让 Codex 看到什么命令就直接跑。

涉及服务器权限，我会停一下。  
涉及后台账号、密钥、token，我不会随便贴。  
涉及支付、订单、客户数据，我会更谨慎。  
涉及插件，我也不会它推荐什么就装什么。

WordPress 插件多，是优点。

但插件装多了，也会带来速度、冲突、安全问题。

所以我现在会把 Codex 当成一个帮我查问题、解释报错、整理步骤的人。

但最后要不要装插件，怎么装，装完能不能留，还是我自己看。

这个判断不能省。

## 回头看，我的结论是

表面上看，我是用 Codex 连 VPS，搭了一个 WordPress 独立站。

但更准确地说，是我在做一个选择：

我会用 Next.js，但这次独立站不适合所有东西都自己写。  
Shopify 省心，但我这次想要更高自由度。  
WordPress 麻烦，但它的后台和插件更适合这类站。  
我不熟 WordPress，所以让 Codex 帮我把它先搭起来。

AI 对我有用的地方，不是让我什么都不用学。

它更像是在我已有能力旁边，补一段我暂时不熟的能力。

网站建起来只是开始。

后面我还想继续试：能不能把 Figma 里的风格、Google Drive 里的图片、产品表格、SEO 内容，慢慢接到这个 WordPress 站里。

如果这些能跑起来，这个站就会少一点尝鲜感。

它会变成我做独立站时，真的能反复用的一套做事方式。

下一篇我会接着讲：站跑起来以后，我为什么先去整理 Figma 里的网站风格。

因为页面不能各长各的样子。
